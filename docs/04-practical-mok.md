# Practical MOK Setup

## Introduction

The previous chapters explained Secure Boot, MOK, kernel module signing, and `akmods`.

This chapter moves from concepts to the practical Fedora workflow for preparing an `akmods` signing key, requesting MOK enrollment, completing the enrollment through the boot environment, and verifying the result.

The workflow is:

```text
Check Secure Boot
        ↓
Check akmods tools
        ↓
Create or reuse signing key
        ↓
Inspect public certificate
        ↓
Request MOK enrollment
        ↓
Reboot
        ↓
MokManager
        ↓
Enroll MOK
        ↓
Boot Fedora
        ↓
Verify enrollment
        ↓
Build and sign external modules
```

The private key remains on the system and must be protected.

---

## Before You Start

This chapter assumes:

* Fedora Linux is running in UEFI mode
* Secure Boot is enabled
* You have administrative access through `sudo`
* The system uses `akmods` for external kernel modules

Check the current Secure Boot state:

```bash
mokutil --sb-state
```

Expected output when Secure Boot is enabled is similar to:

```text
SecureBoot enabled
```

If Secure Boot is disabled, the MOK workflow can still be prepared, but Secure Boot is not currently enforcing the firmware trust path.

This chapter focuses on a system where Secure Boot is enabled.

---

## Check the Required Tools

Check whether `akmods` is installed:

```bash
rpm -q akmods
```

Check the relevant commands:

```bash
command -v akmods
command -v kmodgenca
command -v mokutil
command -v openssl
```

If the required packages are missing, install them:

```bash
sudo dnf install akmods mokutil
```

The Fedora `akmods` package provides the `kmodgenca` utility and the key infrastructure used by the `akmods` Secure Boot workflow.

The exact package set can vary depending on what is already installed on the system.

---

## Understand the `akmods` Signing Key

The `akmods` workflow uses a key pair:

* A private key
* A public X.509 certificate

The private key signs kernel modules.

The corresponding public certificate is used to verify those signatures.

Conceptually:

```text
Private key
    │
    │ signs
    ▼
Kernel module
    │
    │ verified with
    ▼
Public certificate
```

The public certificate is the part that can be enrolled as a MOK.

The private key must remain secret.

---

## Check for an Existing Key Pair

Before generating anything, check whether the `akmods` certificate already exists:

```bash
sudo ls -l /etc/pki/akmods/certs/
```

Then check the private-key directory:

```bash
sudo ls -l /etc/pki/akmods/private/
```

A standard `akmods` setup uses:

```text
/etc/pki/akmods/certs/public_key.der
```

for the public certificate.

The corresponding private key is stored under:

```text
/etc/pki/akmods/private/
```

Do not assume that a certificate file is trusted merely because it exists on disk.

---

## Generate the `akmods` Key Pair

If the expected key pair does not already exist, generate it with:

```bash
sudo kmodgenca -a
```

The `-a` option uses the default `akmods` key-generation settings.

If an existing key pair is detected, `kmodgenca` warns instead of silently replacing it.

Do not force regeneration simply because a module is failing to load.

An existing key may already be enrolled as a MOK and may already be associated with previously signed modules.

The important principle is:

> Reuse an existing signing key unless there is a deliberate reason to replace it.

---

## When Key Regeneration Is Appropriate

Replacing the signing key should be treated as a deliberate key-management operation.

Examples include:

* The private key was compromised
* The private key was permanently lost
* A key-rotation policy requires replacement
* The system is being rebuilt and the previous key is intentionally retired

Do not use forced key generation as a generic troubleshooting command.

If a new key is generated, the new public certificate must be enrolled separately before it can provide the intended trust relationship.

---

## Inspect the Generated Certificate

Once the key pair exists, inspect the certificate:

```bash
sudo ls -l /etc/pki/akmods/certs/public_key.der
```

Then inspect its X.509 information:

```bash
openssl x509 \
    -inform DER \
    -in /etc/pki/akmods/certs/public_key.der \
    -noout \
    -subject \
    -issuer \
    -fingerprint \
    -dates
```

This identifies the certificate you are preparing to enroll.

At this stage:

```text
Certificate exists
        ≠
Certificate is enrolled
        ≠
Certificate is being used to sign a module
```

These are separate states.

---

## Verify the Certificate Format

`mokutil --import` is used here with the DER-encoded X.509 certificate generated by the `akmods` signing workflow.

The standard `akmods` public certificate is:

```text
/etc/pki/akmods/certs/public_key.der
```

You can inspect the file type with:

```bash
file /etc/pki/akmods/certs/public_key.der
```

Do not convert or replace the certificate unless there is a specific reason to do so.

---

## Check Whether the Key Is Already Enrolled

Before requesting a new enrollment, test the existing certificate:

```bash
sudo mokutil --test-key /etc/pki/akmods/certs/public_key.der
```

`mokutil --test-key` checks whether the specified key is already enrolled.

If the key is already enrolled, there is normally no reason to import it again.

You can also list the enrolled MOKs:

```bash
sudo mokutil --list-enrolled
```

The list may contain several certificates, including keys unrelated to `akmods`.

Do not assume that every enrolled key belongs to the current module-signing workflow.

---

## Request MOK Enrollment

If the certificate is not already enrolled, request enrollment with:

```bash
sudo mokutil --import /etc/pki/akmods/certs/public_key.der
```

`mokutil --import` creates an enrollment request for the key. It does not by itself complete the MOK enrollment.

You will be asked to create a temporary password.

This password is used later by the boot-time MOK management environment.

It is not the private-key password.

---

## The MOK Enrollment Password

The password created during:

```bash
sudo mokutil --import /etc/pki/akmods/certs/public_key.der
```

is associated with the pending MOK operation.

It is not:

* The Linux user password
* The `sudo` password
* The private signing key
* The Secure Boot Platform Key password

It is temporary authorization for the pending MOK operation.

Keep it available until the enrollment has been completed.

---

## Check the Pending Enrollment

Before rebooting, inspect pending enrollment requests:

```bash
sudo mokutil --list-new
```

`mokutil --list-new` displays keys that are currently waiting to be enrolled.

You can compare this with the currently enrolled keys:

```bash
sudo mokutil --list-enrolled
```

The requested certificate should not be treated as enrolled until the boot-time enrollment has been completed.

---

## Reboot Into the MOK Management Environment

Once the request is ready:

```bash
sudo reboot
```

During the next boot, the system may enter the MOK management environment provided by the boot chain.

The exact screen and wording can vary.

The important point is that the pending enrollment requires confirmation during boot.

---

## Enroll the MOK

The exact menu wording can vary, but the process generally follows this pattern:

```text
MOK management
      ↓
Enroll MOK
      ↓
Continue
      ↓
Confirm enrollment
      ↓
Enter the temporary password
      ↓
Reboot
```

Follow the prompts shown by the system.

Do not assume that the menu will look identical on every Fedora installation.

The important operation is to explicitly approve the pending certificate enrollment.

---

## Why Boot-Time Confirmation Matters

The MOK workflow separates the creation of an enrollment request from its final approval.

Conceptually:

```text
mokutil --import
        ↓
Pending enrollment
        ↓
Reboot
        ↓
MOK management environment
        ↓
User confirmation
        ↓
MOK enrolled
```

This makes the enrollment an explicit boot-time operation rather than an immediate userspace change.

---

## Verify the Enrollment

After Fedora boots again, test the certificate directly:

```bash
sudo mokutil --test-key /etc/pki/akmods/certs/public_key.der
```

A successful result confirms that the specified certificate is enrolled.

You can also list all enrolled keys:

```bash
sudo mokutil --list-enrolled
```

The direct `--test-key` check is especially useful because it tests the exact certificate you intended to enroll.

---

## Verify Secure Boot Again

Check the Secure Boot state:

```bash
mokutil --sb-state
```

The expected result for this workflow is:

```text
SecureBoot enabled
```

This confirms that Secure Boot is still enabled after the MOK enrollment.

MOK enrollment should not require disabling Secure Boot.

---

## MOK Enrollment Does Not Sign Modules

Enrolling the certificate does not modify existing kernel modules.

The operations are separate:

```text
MOK enrollment
    ↓
Makes the public key available to the trust path

Module signing
    ↓
Uses the private key to create a module signature
```

Therefore, a module that was built without an appropriate signature is not fixed merely because the corresponding public certificate has been enrolled.

The module must still be built and signed correctly.

---

## Verify a Signed Module

After an external module has been built, inspect its signature metadata:

```bash
modinfo -F signer <module>
```

For example:

```bash
modinfo -F signer nvidia
```

You can also inspect:

```bash
modinfo -F sig_id <module>
modinfo -F sig_key <module>
```

These commands provide information stored in the module's signature metadata.

As explained in Chapter 3, this information is useful for diagnosis but does not by itself prove that the kernel will trust the signing key.

---

## Keep Three States Separate

During troubleshooting, distinguish:

### Key generation

```text
Private key
     +
Public certificate
```

### MOK enrollment

```text
Public certificate
        ↓
Enrolled MOK
```

### Module signing

```text
Private key
        ↓
Signed module
```

The desired relationship is:

```text
Signed module
      ↓
Corresponding public certificate
      ↓
Certificate available through the kernel trust path
      ↓
Signature can satisfy the kernel's requirements
```

A failure at any stage can prevent a module from loading.

---

## Check Before Generating a New Key

A common mistake is generating a new key every time a module fails.

Before doing that, check:

```bash
sudo ls -l /etc/pki/akmods/certs/
```

Then:

```bash
sudo mokutil --test-key /etc/pki/akmods/certs/public_key.der
```

If the existing certificate is already enrolled, keep using it unless there is a specific reason to rotate the key.

Creating a second key can make troubleshooting harder because there may then be multiple certificates and multiple possible signing keys.

---

## Protect the Private Key

The private key is the security-sensitive part of the signing system.

Check its permissions:

```bash
sudo ls -l /etc/pki/akmods/private/
```

Do not:

* Commit the private key to Git
* Upload it to GitHub
* Place it in a public directory
* Share it unnecessarily
* Store an unprotected copy in a cloud drive

The public certificate can be distributed for enrollment.

The private key should remain protected.

A compromised signing key can allow an attacker to create modules signed with a key that the system trusts.

---

## Backing Up the Key

A signing key may be useful for maintaining an existing installation because future modules can continue to be signed with the same key.

If the private key is lost, a new key can be generated, but the new public certificate establishes a different trust relationship and must be enrolled separately.

If the key is backed up, protect the backup appropriately:

* Encrypt it
* Restrict access
* Store it separately from public repositories
* Document what the key is used for

Do not create an unencrypted backup simply for convenience.

---

## Troubleshooting MOK Enrollment

### `mokutil --import` reports that the key is already enrolled

Test the certificate directly:

```bash
sudo mokutil --test-key /etc/pki/akmods/certs/public_key.der
```

If it is already enrolled, there is normally no need to import it again.

---

### The key appears in the pending list but not the enrolled list

Check:

```bash
sudo mokutil --list-new
```

If the key is still pending, the boot-time MOK enrollment has not been completed.

Reboot and complete the MOK management process.

---

### The MOK management screen did not appear

Do not immediately generate another key.

First inspect:

```bash
mokutil --sb-state
sudo mokutil --list-new
```

If the request is still pending, investigate the boot environment before changing the key configuration.

The exact MOK management behavior can depend on the installed boot components and platform.

---

### The key is enrolled but the module still does not load

MOK enrollment alone does not prove that the module is correctly signed.

Check:

```bash
modinfo -F signer <module>
modinfo -F sig_id <module>
modinfo -F sig_key <module>
```

Then inspect kernel messages:

```bash
journalctl -k -b | grep -Ei 'module|signature|verification|secure boot'
```

Possible causes include:

* The module is unsigned
* The module was signed with a different key
* The signature is invalid
* The module was built for another kernel
* The module has missing dependencies
* The problem is unrelated to Secure Boot

Diagnose the actual failure before changing the MOK configuration.

Before moving to the next chapter:

```text
[ ] Secure Boot is enabled
[ ] akmods is installed
[ ] kmodgenca is available
[ ] An akmods key pair exists
[ ] The public certificate has been inspected

[ ] The MOK was confirmed during boot
[ ] mokutil --test-key confirms enrollment
[ ] Secure Boot remains enabled
[ ] The private key remains protected
```

At this point, the MOK trust material is prepared.

## Summary

The practical MOK workflow is:

```text
Check Secure Boot
        ↓
Check akmods tools
        ↓
Check for an existing key
        ↓
Generate a key only if necessary
        ↓
Inspect the public certificate
        ↓
Check whether it is already enrolled
        ↓
mokutil --import
        ↓
Reboot
        ↓
MOK management
        ↓
Enroll MOK
        ↓
Boot Fedora
        ↓
mokutil --test-key
        ↓
Verify Secure Boot
        ↓
Build and sign external modules
```

The most important rules are:

1. **Do not generate a new signing key unnecessarily.**
2. **Do not confuse the public certificate with the private signing key.**
3. **Do not confuse MOK enrollment with module signing.**
4. **Verify the exact certificate you intended to enroll.**
5. **Keep Secure Boot enabled while troubleshooting whenever possible.**
6. **Protect the private signing key.**

MOK enrollment prepares the trust relationship. It does not replace the module-signing process.

The next chapter will connect this trust setup to the actual `akmods` build and signing workflow.
