# Machine Owner Key (MOK)

## Introduction

**MOK (Machine Owner Key)** is a mechanism used on Linux systems to allow the system owner to enroll additional trusted keys.

MOK is particularly useful when **Secure Boot** is enabled and the system needs to trust software that is not signed by one of the keys already trusted by the platform.

A common example is a third-party kernel module.

The important idea is simple:

> **MOK allows the owner of a machine to extend the system's trusted key material without disabling Secure Boot.**

MOK therefore complements Secure Boot rather than replacing it.

---

## Why Is MOK Needed?

Secure Boot relies on a chain of cryptographic trust.

The firmware has a set of trusted keys and uses them to determine whether certain boot components are allowed to execute.

However, a Linux system may also need software that comes from outside the distribution's standard signing infrastructure.

Examples include:

* Third-party kernel modules
* Locally built kernel modules
* Hardware drivers built outside the standard Fedora kernel packages
* Modules generated by external build systems

If such a module is not signed with a key that the system already trusts, the kernel may refuse to load it when module signature enforcement is active.

MOK provides a way to introduce an additional trusted signing key.

The simplified process is:

```text
Generate key pair
       │
       ▼
Sign kernel module
       │
       ▼
Enroll public key as MOK
       │
       ▼
Kernel can recognize the signature
```

The private key remains with the system owner or build system, while the public key is enrolled into the system's trusted key material.

---

# Public and Private Keys

MOK uses public-key cryptography.

A key pair consists of:

```text
Private Key
     │
     └── Used to create signatures

Public Key
     │
     └── Used to verify signatures
```

These two keys have different roles.

## Private Key

The private key is used to sign software.

It must be protected carefully.

Anyone who obtains the private key may be able to create signatures that the corresponding public key will recognize as valid.

For this reason:

> **The MOK private key should never be shared publicly or committed to a Git repository.**

It should also not be placed in a publicly accessible backup without appropriate protection.

---

## Public Key

The public key is used to verify signatures created with the corresponding private key.

Unlike the private key, the public key is intended to be distributed.

When a public key is enrolled as a MOK, the system can use that key as part of its trusted key material.

A simplified relationship is:

```text
Private Key
     │
     │ signs
     ▼
Kernel Module
     │
     │ verified using
     ▼
Public Key
     │
     ▼
Enrolled MOK
```

---

# MOK and Secure Boot

MOK and Secure Boot are closely related, but they are different mechanisms.

### Secure Boot

Secure Boot is provided by the UEFI firmware and establishes trust during the early boot process.

### MOK

MOK provides an additional mechanism for enrolling owner-controlled keys.

### Module Signing

Module signing applies a cryptographic signature to a kernel module.

These mechanisms can work together:

```text
UEFI Secure Boot
       │
       ▼
Trusted boot chain
       │
       ▼
Linux Kernel
       │
       ▼
Module signature verification
       │
       ▼
Trusted signing key
       │
       ├── Distribution key
       │
       └── Enrolled MOK
```

The exact trust path depends on the platform, firmware, bootloader, kernel configuration, and distribution implementation.

Therefore, it is better to think of MOK as **additional trusted key material** rather than as a replacement for Secure Boot.

---

# How MOK Enrollment Works

MOK enrollment is intentionally designed to require user interaction.

A typical workflow looks like this:

```text
Create or obtain a signing key
          │
          ▼
Prepare the public key for enrollment
          │
          ▼
Request MOK enrollment
          │
          ▼
Reboot
          │
          ▼
UEFI/MOK enrollment interface
          │
          ▼
User confirms enrollment
          │
          ▼
Key becomes enrolled
```

The exact commands used to create and enroll a key depend on the workflow being used.

This project will cover the practical Fedora workflows in later chapters.

---

# Why Does Enrollment Require a Reboot?

MOK enrollment is handled outside the normal Fedora userspace.

The enrollment process occurs during system startup through the firmware/boot environment before the normal operating system session is available.

This provides an important security property:

> A process running normally inside Fedora should not be able to silently enroll a new trusted key without explicit authorization.

The user is therefore presented with an enrollment interface during reboot.

The exact appearance of this interface may vary between systems and boot configurations.

---

# The MOK Enrollment Screen

When a pending MOK enrollment request exists, the system may display a firmware-style enrollment interface during boot.

The available options can vary, but commonly include actions such as:

* Continue boot
* Enroll MOK
* View key
* Delete MOK
* Continue without enrolling

The important point is that **creating a key is not the same as enrolling it**.

A key can exist on the filesystem without being trusted by the system.

Enrollment is the step that tells the system to recognize the public key as trusted MOK material.

---

# Enrollment Password

Many MOK enrollment workflows use a temporary password to confirm the enrollment request during reboot.

This password is not the private-key password.

These are separate concepts.

For example:

```text
MOK enrollment password
        │
        └── Confirms the pending enrollment request

Private-key password
        │
        └── Protects the private signing key
```

The enrollment password is normally created when the enrollment request is prepared and then entered during the firmware/boot enrollment interface.

Its purpose is to provide an explicit confirmation step.

---

# Where Are MOKs Stored?

An enrolled MOK is not simply a normal file in the user's home directory.

The enrolled key becomes part of the system's trusted key infrastructure.

Linux can expose trusted keys through kernel keyrings and related interfaces.

This distinction is important:

```text
Public key file
     │
     ├── Exists on disk
     │
     └── May or may not be enrolled

Enrolled MOK
     │
     └── Recognized as trusted key material
```

Therefore, having a `.der`, `.crt`, or similar public-key file on disk does **not** by itself mean that the key is trusted.

---

# Checking Enrolled MOKs

A useful diagnostic step is to inspect the MOK database.

On Fedora systems, the `mokutil` utility is commonly used for this purpose.

To list enrolled keys:

```bash
mokutil --list-enrolled
```

This is a **read-only inspection command**.

It does not enroll or remove a key.

A typical output contains certificate information for each enrolled key.

The exact output varies depending on the system.

---

# Checking Secure Boot State

`mokutil` can also be used to check whether Secure Boot is currently enabled:

```bash
mokutil --sb-state
```

Typical output may indicate:

```text
SecureBoot enabled
```

or:

```text
SecureBoot disabled
```

This is useful when troubleshooting because the behavior of kernel module signature enforcement can differ depending on the Secure Boot state and kernel configuration.

---

# MOK Enrollment Is Not Module Signing

One of the most common misunderstandings is treating MOK enrollment and module signing as the same operation.

They are separate.

For example:

```text
Step 1
Create signing key
        │
        ▼
Step 2
Enroll public key as MOK
        │
        ▼
Step 3
Sign kernel module with private key
        │
        ▼
Step 4
Kernel verifies module signature
```

The public key must correspond to the private key used to sign the module.

If a module is signed with a different private key, enrolling an unrelated MOK will not make that signature trusted.

---

# One MOK Can Be Used for Multiple Modules

A signing key can be used to sign multiple kernel modules.

For example:

```text
                 MOK private key
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Module A      Module B      Module C
          │            │            │
          └────────────┼────────────┘
                       ▼
                 Verified using
                 MOK public key
```

This is one reason automated systems such as `akmods` can use a persistent signing key for modules built for different kernel versions.

The exact key-management workflow should still be understood before relying on automation.

---

# MOK and Kernel Updates

A kernel update can introduce a new kernel version while external kernel modules may need to be rebuilt for that version.

For example:

```text
Kernel 1
   │
   ├── Module A
   └── Module B

Kernel update
   │
   ▼

Kernel 2
   │
   ├── Module A rebuilt
   └── Module B rebuilt
```

The new modules must still satisfy the kernel's signature requirements.

This is one reason tools such as `akmods` are important on Fedora systems using external kernel modules.

Later chapters will explain how module rebuilding and signing fit together.

# Security Considerations

MOK provides useful flexibility, but enrolling a key changes the system's trust configuration.

A MOK should therefore be treated as a security-sensitive credential.

## Protect the Private Key

The private key should be stored securely.

Do not:

* Commit it to Git
* Upload it to a public repository
* Share it unnecessarily
* Leave it in an unprotected public directory

For example, a repository should never contain files such as:

```text
mok.key
private.key
signing.key
```

unless they are explicitly test keys with no security value.

---

## Verify the Key Before Enrollment

Before enrolling a public key, the system owner should understand:

* Where the key came from
* Who generated it
* What it will be used to sign
* Where the corresponding private key is stored

Enrolling an unknown key reduces the value of the trust model because software signed by that key may subsequently be recognized as trusted.

---

## Do Not Enroll Keys Blindly

A common troubleshooting mistake is to treat MOK enrollment as a generic solution:

> "Secure Boot is blocking the driver, so enroll this key."

That approach is unsafe without understanding where the key came from and what it is intended to trust.

A better approach is:

```text
Identify the module
        │
        ▼
Identify its signing key
        │
        ▼
Verify the key
        │
        ▼
Enroll only if trusted
```

---

# Removing a MOK

MOK enrollment is not necessarily permanent.

A previously enrolled key can be removed through the appropriate MOK management workflow.

This can be useful when:

* A signing key is no longer needed
* A key has been replaced
* A test key should be removed
* A private key may have been compromised

Removing a MOK can also cause modules signed exclusively with that key to stop being accepted.

Therefore, MOK removal should be treated as a system configuration change rather than a harmless cleanup operation.

# MOK and `akmods`

Fedora commonly uses **`akmods`** to build external kernel modules.

A simplified workflow can look like:

```text
Kernel update
      │
      ▼
akmods builds external module
      │
      ▼
Module is signed
      │
      ▼
Kernel verifies signature
      │
      ▼
Module loads
```

When Secure Boot is enabled, signing becomes especially important because the kernel may enforce module signature verification.

The details of how `akmods` generates, stores, and uses signing keys will be covered in the dedicated module-signing chapter.

---

# What MOK Does Not Do

MOK does not:

* Disable Secure Boot
* Automatically sign kernel modules
* Automatically make every third-party driver trusted
* Replace the UEFI Secure Boot trust mechanism
* Guarantee that software is safe
* Remove the need to protect the private signing key

MOK only provides a mechanism for adding trusted key material to the system.

The software signed by that key still needs to be understood and trusted by the system owner.

---

# Practical Mental Model

A simple way to remember the relationship is:

```text
Secure Boot
    │
    │ establishes trust
    ▼
Boot process
    │
    ▼
Linux Kernel
    │
    │ verifies
    ▼
Kernel Modules
    │
    │ using trusted keys
    ▼
┌─────────────────────┐
│ Fedora keys         │
│ MOK-enrolled keys   │
└─────────────────────┘
```

Or, even more simply:

> **Secure Boot establishes the security model.**
>
> **MOK adds an owner-controlled trusted key.**
>
> **Module signing uses that key to prove who signed a module.**

---

# Summary

MOK is a mechanism that allows the owner of a system to enroll additional trusted public keys.

It becomes particularly important when Secure Boot is enabled and the system needs to load third-party or locally built kernel modules.

The most important distinctions are:

1. **Secure Boot** — establishes trust during the boot process.
2. **MOK enrollment** — adds an owner-controlled public key to the trusted key material.
3. **Private key** — signs kernel modules and must be protected.
4. **Module signature** — proves that a module was signed by the corresponding private key.
5. **Kernel verification** — determines whether the module's signature is trusted.

Understanding these relationships is essential before troubleshooting third-party kernel modules on Fedora.

The next chapter will examine **kernel module signing and `akmods`**, including how Fedora builds external modules and how Secure Boot affects their loading.
